# ۵. نماینده با حداقل دسترسی

[فهرست](README.md)

حساب نمایندهٔ نمونه با رمز ثابت وجود ندارد. مالک باید نقش مناسب بسازد و سپس مدیر را به آن نقش متصل کند. قابلیت RBAC از PasarGuard به ارث رسیده است.

## ساخت نقش

۱. با مالک بخش نقش مدیران / Admin roles را باز کن.
۲. نقش جدید مثل «نماینده محدود» بساز.
۳. در دسترسی کاربران، عملیات مورد نیاز create/read/read_simple/update را به **OWN / فقط کاربران خود** محدود کن. در API این scope برابر 1 است؛ ALL برابر 2 است.
۴. delete، reset usage، revoke sub را فقط اگر نماینده نیاز دارد فعال کن.
۵. خواندن سادهٔ گروه و خواندن قالب‌ها را به اندازهٔ نیاز بده.
۶. دسترسی cores، nodes، settings، admins، roles و set_owner را بدون ضرورت فعال نکن.
۷. در Access، allowed_group_ids و allowed_template_ids را محدود کن؛ برای فروش بر اساس پلن `require_template` را فعال کن.
۸. سقف تعداد کاربر/حجم/بازهٔ انقضا و رفتار بعد از اتمام سهمیه را متناسب با سیاست خودت تنظیم کن.

## ساخت مدیر نماینده

در مدیران / Admins، نام یکتا، رمز قوی، نقش تازه و سهمیه را مشخص کن. رمز را جداگانه و امن تحویل بده. صفر/خالی بودن limit را بدون بررسی معنی نامحدود فرض نکن؛ رفتار فیلد مربوطه را در رابط و مستندات نسخه ببین. نقش مالک را به نماینده نده.

## آزمون جداسازی ضروری

دو نمایندهٔ آزمایشی A و B و برای هر کدام یک کاربر بساز. در مرورگر خصوصی جدا:

- A فقط کاربران خودش را ببیند؛ B همین‌طور.
- A با دانستن نام کاربر B نتواند او را بخواند، تغییر دهد یا حذف کند.
- نماینده نتواند تنظیمات هسته یا نود را تغییر دهد.
- تمام‌شدن سهمیه رفتار مورد انتظار داشته باشد.

«مخفی‌شدن دکمه» به تنهایی کافی نیست؛ API هم باید درخواست را رد کند. آزمون‌های محدود CI جای بررسی همهٔ ترکیب‌های RBAC، override و محدودیت‌ها را نمی‌گیرند.

## خطاهای رایج

403 بعد از انتخاب قالب: مجوز read template / گروه یا allowed ids را بررسی کن. کاربر بدون کانفیگ: گروه و tag ورودی را بررسی کن. امکان دیدن کاربران دیگر: فوراً دسترسی را قطع و scope و permission override را بررسی کن؛ رمز را تنها عامل امنیت ندان.
