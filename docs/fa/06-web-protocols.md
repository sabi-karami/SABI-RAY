# ۶. پروتکل‌های وب

[فهرست](README.md)

VLESS، VMess و Trojan پروتکل‌اند؛ WebSocket، HTTPUpgrade و XHTTP روش انتقال‌اند؛ TLS لایهٔ امنیت ارتباط است. تفاوت اسم یا fingerprint به تنهایی پینگ کمتر تضمین نمی‌کند.

| مقدار SABI_PROFILES | پروتکل | مسیر | حالت |
|---|---|---|---|
| vless-ws | VLESS | WS پشت TLS | پیش‌فرض |
| trojan-ws | Trojan | WS پشت TLS | پیش‌فرض |
| vmess-ws | VMess | WS پشت TLS | پیش‌فرض |
| vless-upgrade | VLESS | HTTPUpgrade پشت TLS | اختیاری |
| vless-xhttp | VLESS | XHTTP packet-up پشت TLS | اختیاری |

برای فعال‌کردن هر پنج مورد **پیش از نصب جدید**:

```dotenv
SABI_PROFILES=vless-ws,trojan-ws,vmess-ws,vless-upgrade,vless-xhttp
```

بعد از نصب فقط این خط را تغییر نده؛ state جلوی تغییر بی‌برنامه را می‌گیرد. دامنهٔ خروجی از PUBLIC_DOMAIN، پورت 443، TLS روشن و بررسی گواهی روشن است. مسیر تصادفی هر نصب پایدار می‌ماند؛ آن را دستی در nginx عوض نکن.

## نکات سازگاری

- WebSocket معمولاً با edgeهای HTTP سازگارتر است، اما timeout و محدودیت میزبان همچنان مهم است.
- HTTPUpgrade نیازمند پشتیبانی مشخص کلاینت است؛ صرف دیدن VLESS در فهرست اپ کافی نیست.
- XHTTP این نسخه packet-up است. کلاینت و CDN باید همان حالت و مسیر را بفهمند؛ redirect یا buffering واسطه ممکن است اختلال بسازد.
- ALPN، host، SNI و path را از لینک تولیدی نگه دار. «تست برای سبزشدن» با خاموش‌کردن TLS verification راه‌حل نیست.
- پنج کانفیگ وب روی یک نود، پنج کشور یا IP خروجی مستقل نیستند.

## آزمایش مرحله‌ای

۱. دامنهٔ HTTPS و `/healthz` را بررسی کن.
۲. کاربرِ دارای گروه بساز.
۳. ساب را در کلاینت جدید import کن.
۴. اول VLESS/WS را با URL test امتحان کن.
۵. سپس هر گزینه را جدا انتخاب و صفحهٔ وب واقعی باز کن.
۶. تست موفق/ناموفق و نسخهٔ کلاینت را ثبت کن؛ DNS و TCP ping را با تست کامل یکی ندان.

CI انتقال دادهٔ محلی را آزمایش می‌کند. مسیر خارجی TLS و اینترنت همراه/ثابت تو باید جدا تست شود.
